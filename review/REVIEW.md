# ClipForge review

## Summary

Reviewed on 2026-11-01 at commit `ace2d22731bbb07236dfe9e6e3f8b481fa450a4c` (initial working tree clean). ClipForge has a credible offline capture-to-edit workflow, with sensible separation between pure media calculations and process orchestration. The sandboxed renderer, argument-array process launches, segment reference counts, and temporary-output validation are good foundations (`src/main/main.ts:82`, `src/main/util.ts:56`, `src/main/capture/replayBuffer.ts:68`, `src/main/export/exportService.ts:57`). I would keep Electron and FFmpeg for the next iteration. The urgent work is making an accepted save survive a slow preceding save, stop, and restart, and making editor changes survive navigation. Export finalization, corrupt metadata recovery, and privileged input validation also need attention before adding a large feature set. Passing the current pure unit tests would not establish lifecycle reliability; there are no CaptureService, ExportService, protocol, or renderer unit tests in the four existing test files. The biggest experiential improvement after reliability is confidence while playing: an audible save confirmation, clear source selection, and game-aware organization. Native capture deserves a measured prototype, not a wholesale rewrite based on assumed zero-copy savings. No app, capture, integration, or desktop automation was started during this review.

## Opinions

**Keep FFmpeg capture for now; create a backend seam.** `ddagrab -> hwdownload -> scale/format -> encode` explicitly forces CPU readback (`src/main/capture/captureArgs.ts:60`). At 1080p60, BGRA alone represents about 0.50 GB/s of raw frames; at 1440p60 about 0.88 GB/s, before additional copies/conversion/upload. These are calculated data rates, not measured PCIe traffic or game FPS loss. A GPU-resident path may work when capture, conversion and AMF share a suitable adapter/device, but the reported dual-GPU failure is a reason to keep the existing fallback. Do not call a path zero-copy without confirming device identity and tracing transfers.

Try capability-detected FFmpeg `gfxcapture` before building a complete replacement: upstream exposes HWND/executable/window selectors ([FFmpeg source](https://ffmpeg.org/doxygen/trunk/vsrc__gfxcapture_8c_source.html)). The installed build's `-h filter=gfxcapture` and actual behavior, including static/minimized/resized windows, must be checked by the owner; upstream trunk is not proof of the shipped binary's features. A later native WGC/DXGI -> GPU color conversion -> AMF backend can provide frame timestamps and adapter control. [Microsoft's capture documentation](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) describes window/display capture, QPC timestamps, resizing, and the need for float-format handling/tone mapping for HDR. WGC does not guarantee exclusive-fullscreen/protected-content success; do not introduce injection or DRM bypass. Current code has no explicit HDR tone-map/color-management path (`src/main/capture/captureArgs.ts:60`); flag HDR unsupported until test patterns and SDR export colors are verified.

Measure baseline and each prototype in the same game/scene at 1080p60 and 1440p60: average FPS, 1% low, CPU/GPU load, encode speed, dropped frames, save latency and output quality. Suggested owner-adjustable adoption gate: at least 20% relative reduction in capture overhead or a material source-selection benefit, without worse reliability. Start with a suggested <=3% average game-FPS and <=5% 1%-low regression budget against capture-off; these are proposed targets, not current results. Do not discard the working backend because a synthetic encoder benchmark is faster.

**Per-process audio is higher value than speculative capture rewrites.** Today one output endpoint captures Discord/browser/system sounds too (`native/AudioCap/Program.cs:54`). Add an optional process-tree include mode via `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, keeping endpoint loopback as a fallback. Microsoft's [application-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/) specifies build 20348 or later; ordinary older Windows 10 installations must not be assumed compatible. Keep mic separate and visibly label what is captured. A two-hour owner test should use simultaneous visible flashes and audio clicks at start and intervals, multiple endpoint rates, silence/bursts, and device loss; proposed acceptance is absolute A/V offset <=80 ms and change <=20 ms/hour, with no silent queue losses. These are targets requiring measurement.

**Keep the disk ring; make precision optional.** At High/1080p60 the configured nominal 24 Mbps means roughly 3 MB/s or 10.8 GB/hour written, plus audio/TS overhead (`src/main/capture/captureArgs.ts:16`, `:31`). A 126 s ring is roughly 378 MB nominal, not 10.8 GB retained. VBR peaks and queued-save reservations raise the bound. A compressed RAM ring trades SSD writes for hundreds of MB of memory and loses crash recovery; an uncompressed BGRA 1080p60 two-minute ring would be about 60 GB. Neither should be the default now. For tighter saves, preserve fast remux as default and offer frame-accurate re-encoding later; `-c copy` cannot promise arbitrary frame-accurate start cuts between IDRs. Shorter GOP/segments are another benchmarkable latency/bitrate tradeoff, not a free fix. Current save waits for segment close, so the endpoint can include post-press frames; distinguish endpoint latency from the roughly one-segment duration excess (`src/main/capture/captureService.ts:344`, `src/main/capture/replayBuffer.ts:50`).

**Keep JSON until there is a demonstrated query/scale need.** Atomic writes are a good start; backup recovery, validation and surfaced failures are missing. SQLite becomes attractive for thousands of indexed clips, markers and transactional bulk operations, but it does not repair save races or source identity. The main-process synchronous metadata path is serialized today; do not invent simultaneous JS-thread JSON writers. The real concurrency concerns are asynchronous task results and crash windows.

**Split orchestration at the behaviors being fixed.** These files are moderately sized, not justification for a framework rewrite.
